Companion to “Cryptography in Online Multiplayer Games”

Game Crypto Lab

Five hands-on demos that run real cryptography in your browser (Web Crypto API). Encrypt a game packet and tamper with it, run a key exchange with and without a man in the middle, forge a session token, replay packets, and try to duplicate an item on a signed ledger.

AES-256-GCM · AEAD

Encrypt a game packet, then attack it

The header (sequence number and player) travels in the clear but is authenticated as associated data. The payload is encrypted. GCM appends a 16-byte tag that covers both.

The 12-byte nonce is built from the sequence number, so every packet gets a unique one, as long as the sequence never repeats under the same key.

TRY THIS
  1. Encrypt and deliver: the server decrypts it.
  2. Click any byte of the ciphertext or tag to flip one bit, then deliver again.
  3. Change the player in the header after encrypting.
  4. Set the sequence back to a number you already used and encrypt: nonce reuse.

Elliptic-curve Diffie–Hellman

Agree on a key over an open network

Alice (the player) and Bob (the server) each make a key pair and swap public keys. Each combines its own private key with the other’s public key and gets the same shared secret. HKDF then turns that secret into one key per direction.

Plain Diffie–Hellman doesn’t say who you’re talking to. Switch on Mallory to see why game servers also sign their half of the handshake.

TRY THIS
  1. Run the handshake: both secrets match.
  2. Turn on Mallory: Alice and Bob now hold different secrets, both known to Mallory.
  3. Also turn on server signatures: Alice spots the swap and aborts.

HMAC-SHA256 · JWT-style

Try to forge a session token

The auth server issues header.payload.signature. The payload is only base64url-encoded, so anyone can read and edit it. The signature is an HMAC keyed with a secret only servers hold.

This game server also pins the algorithm to HS256 and checks the expiry.

TRY THIS
  1. Log in and send the token: accepted.
  2. Click “Make me admin” and send it.
  3. Try the alg: none trick.
  4. Guess the secret and sign it yourself.

Anti-replay sliding window

Replay a packet and get caught

Each packet carries a sequence number that is authenticated with the packet. The receiver remembers which of the last 32 numbers it has seen.

New numbers slide the window forward. Late but unseen packets are accepted, because the internet reorders traffic. Duplicates and packets older than the window are dropped.

TRY THIS
  1. Send a few packets, then send a late one.
  2. Replay a packet you already sent.
  3. Jump far ahead, then send an ancient one.

Signed, hash-chained inventory log

Try to duplicate or steal an item

Every grant and trade becomes an entry. The inventory server hashes it with SHA-256, includes the previous entry’s hash, and signs it with its private key. Anyone holding the public key can audit the whole history.

Trades carry an idempotency key, so a retried or replayed request runs only once. The server also checks the seller actually owns the item.

TRY THIS
  1. Mint a few items and trade them.
  2. Replay the last trade request (a dupe attempt).
  3. Sell an item you don’t own.
  4. Tamper with an old entry, then verify the chain, with and without recomputing its hash.

Everything runs locally in your browser; nothing is sent anywhere. Keys are generated fresh on each page load. These are teaching demos: production games should use vetted libraries and transports (for example Valve’s GameNetworkingSockets, QUIC or DTLS) rather than hand-rolled protocols.
